# travel-buddy：内部是怎么工作的

这是工程记录：流水线、每一道闸门、每一个脚本，以及催生每条规则的那个缺陷。**使用** travel-buddy 完全不需要读它 —— 那部分在 [README](../README_CN.md) 里。它之所以留着，是因为规则的价值等于执行它的东西，而一条丢了理由的规则，迟早会被下一个嫌它碍事的人删掉。

---

## 流水线

```
start_intake_workflow.py
    ├── 没有有效档案？ → 个人档案表单（一次性、需勾选同意、仅本机）
    └── 恰好一个？     → 直接复用、预填，并明确告诉你加载了什么
                    ↓
            本次行程表单（日期/同行/预算/范围 —— 每次都问）
                    ↓
            落盘：plans/intake-*.json  +  plans/next-action-*.json
                    ↓
            run_destination_discovery.py → 仅在显式指定时才拉起一个全新的非交互
                                           Codex/Claude 任务；`auto` 下永不拉起
                    ↓
        Discovery → 候选短名单        Construction → new_plan_skeleton.py → plan JSON
                                              ↓
              并行核验：5 个真实性域 + 2 个审计员   （references/verification.md）
                                              ↓
                                check_plan_contract.py      （字段名，一次报全）
                                              ↓
                                check_plan_consistency.py   （方案与自身是否自洽）
                                              ↓
                                render_final_trip_html.py   （校验方案结构）
                                              ↓
                                validate_trip_html.py       （校验页面）
                                              ↓
                                save_trip_deliverables.py   （全部跑一遍，然后落盘）
                                              ↓
                                check_link_targets.py       （需联网，由你手动跑）
```


## 每个脚本负责判什么

这些你不用自己跑，skill 会跑。之所以列出来，是因为上面那些承诺只值得它背后的东西 —— 这里每一个，都是一条**曾经是散文、现在是程序**的规则。

| 脚本 | 它负责判什么 |
| --- | --- |
| `start_intake_workflow.py` | 在回环地址上起档案表单和行程表单，然后把存好的 intake 路径交回来 |
| `intake_language.py` | 表单用哪种语言打开、用哪种语言回复：`--language`，否则按档案里的偏好，否则按填写档案时页面用的语言，否则中文 |
| `travel_workspace.py` | 创建工作区；只有你勾了同意框才会创建档案 |
| `run_destination_discovery.py` | 仅在你明确要求时：为 Discovery 起一个全新的 Codex/Claude 任务，`auto` 下永不自启；给它的提示会写明与这些脚本同目录的 SKILL.md，以及 intake 记录的语言 |
| `new_plan_skeleton.py` | 产出一份结构合法、等你填内容的方案骨架，让力气花在事实而不是形状上 |
| `check_plan_contract.py` | 闸门之前：这份方案里的每个键，契约都认识吗？它给的是待办清单，不是判决 |
| `check_plan_consistency.py` | 方案与自身对账 —— 路线合计、步行、饭点是否落在营业时间内、预算算术 |
| `render_final_trip_html.py` | 缺必需结构的方案直接拒绝渲染；负责把页面建出来 |
| `validate_trip_html.py` | 校验页面本身 —— 必需区块、真正的导航链接、非英文页面上不许留英文 |
| `plan_flags.py` | 从方案推导页面检查项，于是没有一项能被悄悄关掉 |
| `save_trip_deliverables.py` | 把上面全跑一遍再保存；说不清需求是怎么收集的，就不给存 |
| `plan_to_calendar.py` | 把行程变成 `.ics`，这是这里唯一能进你手机的东西 |
| `new_verification_report.py` | 从方案生成核验报告脚手架，每条结论都留成 `TODO:` |
| `verification_sections.py` | 按段给已核验的方案做指纹，之后哪段改了就只复核哪段 |
| `plan_slice.py` | 给每个核验方一份方案的**投影**，而不是整份文件 |
| `fetch_plan_imagery.py` | 给真实地点配经核验的自由许可照片 —— 达不到标准就一张都不配 |
| `plan_visuals.py` | 用方案里已有的数字画四张内嵌 SVG 图 |
| `check_link_targets.py` | 跟着每个外链按钮走一遍，报出它**实际**落在哪（需要网络） |
| `check_shortlist_consistency.py` | Discovery 的闸门：这些候选真的可比吗，结论诚实吗 |
| `save_discovery_deliverables.py` | 那道闸门一直缺的「门」—— 跑它、盖章、把候选清单写到你其他文件旁边 |
| `replan_trip.py` | 日期一改，它决定的部分重写，其余部分不再算「已核实」 |
| `audit_workspace.py` | 拿今天的闸门回头跑一遍所有已保存的方案，只报告、不改动 |
| `probe_sources.py` | 在有人写下「这个查不到」之前，先问清楚这台机器到底能读到什么 |
| `trip_timer.py` | 记录一次规划真实花掉的时间，并拆成「机器算」和「你在等」 |

## 四道闸门


四道都在 `save_trip_deliverables.py` 里自动执行。值得了解，因为它们查的是**不同的东西**：前两道证明产物「格式规整」，后两道证明它「是真的」—— 后者是结构校验永远够不到的另一个维度。

**`render_final_trip_html.py`** 拒绝渲染结构不全的方案：`route.segments` 数量必须精确等于 `len(stops_in_order) - 1`、每段只能有**一个主要方式**（「地铁/公交/打车」这种选择清单判为含糊）、每个整天都要有午餐**和**晚餐，以及十来条其他规则。

**`validate_trip_html.py`** 检查渲染后的页面。它最锋利的一条规则是：**只要页面 `<html lang>` 不是英文，页面里残留任何渲染器自带的英文就判失败。** 这正是 `plan_status`、预算类别、餐次、交通方式、过敏严重程度、`sources[].confidence` 都被定义成封闭枚举的原因 —— 任意类别字符串无法翻译，就会以英文泄漏到中文页面上。2.2 起这条规则不再依赖一份「已知英文字符串」的手写清单：闸门直接读取渲染器自己的替换表与枚举常量，所以新增的值无需任何人记得去补清单就会被检查。清单本身就是缺陷——`sources[].confidence` 在作者工作区里**十一个**非英文页面上把 `high`、`medium` 当正文打了出来（其中九个是带日期的已交付行程，另两个是渲染预览）；泄漏出某个英文原值的共十三个页面，而工作区里唯一那份盖过闸门章的方案也在其中 —— 两道闸门却都报 VALID。它同时强制：地图按钮必须是真正的导航 URL、大陆路线必须用高德、预订与来源行必须带上可机器校验的属性。2.0 起还会拒绝任何「按钮上写的提供方 ≠ 链接实际打开的域名」的页面：曾有九个按钮写着 *在 KLM 查看选项* 却打开 Google Flights、写着 *在 Google Maps 查看餐厅* 却打开美食博客，而当时所有闸门全绿 —— HTTPS 与唯一性都说明不了链接会去哪里。 2.1 起还会拒绝任何一张不打印评分的餐饮卡：评分只存在 JSON 里、从不渲染到页面上，与压根没去查是同一种缺陷——促成这条规则的那个页面，分数只出现在作者恰好手写进理由文字的地方。

**`plan_flags.py`** 把页面检查项从「让模型回答」改成「从方案推导」。`validate_trip_html.py` 过去把天数、必须出现的预订链接类型、交通方式、以及「未经事实核验」横幅当作四个可选开关，而且**默认全部关闭** —— 于是 `validate_trip_html.py page.html` 会打印 `VALID: booking-ready HTML structure passed.` 并以 0 退出，同时这四项检查一个都没跑；其中三项还依赖 SKILL.md 从未提及的 JSON 字段（`trip.arrival_transport_mode`、`booking_options.attraction_tickets`、`booking_options.ground_transport`），模型得自己想到去翻。而 `save_trip_deliverables.py` 一直都在正确地算这四个值，位置就在那份手写副本二十行之外。现在两个调用方都从这里导入同一份定义：**只要传 `--plan <plan.json>`，就没有任何东西需要回答了。** 不传 `--plan` 时这些开关从「可选」变为「必填」—— 因为退出码 0 正是助手会读到的那个信号。

**`plan_to_calendar.py`** 把计划变成 `.ics` 日历文件，而它是这个 skill 里**唯一能把行程带离笔记本**的东西。这里每一道闸门管的都是交付页面是否**属实**，没有一道管它是否**在旅行者身边**——一个 331 KB 的本地 HTML，人站在琉森街头根本打不开。日历解决这件事不需要服务器、也不需要我们这边的任何账号：文件落进旅行者自己的日历，手机自己同步过去。它还带着页面给不了的两样东西——**一个必须到场的时刻**，以及**一个会响的提醒**：于是「只有 24 个座位，务必提前致电」不再是一句话，而是前一天真的会响起来的闹钟。时间采用浮动本地时间（不带时区），这正是行程表的含义：19:00 就是琉森的 19:00，不管你是在阿姆斯特丹还是在火车上看它。它不编造任何东西——只有计划本身已经带了时间的地方才会产生事件；契约表达不了的，日历也不表达：开口程的回程段**不写任何航线**，因为「每个预订条目一组起讫机场」说不出回程从另一个机场起飞，而把去程反转会得到 `KL1924 GVA → AMS`——那趟航班其实从苏黎世起飞。文件在交付时写在计划旁边，同时以 `data:` URI 内嵌进页面，所以**没有信号时照样能用**，而那正是最需要它的时候。 它的 `DTSTAMP` 取自计划的 `generated_at` 而非当前时钟，所以同一份计划重新渲染会得到完全相同的字节——原先用 `datetime.now()` 时，内嵌日历每次渲染都在变，交付页面因此不可复现，而这件事当时只表现为另一个图片测试（断言两次渲染逐字节相同）偶发失败。

**`new_verification_report.py`** 让核验报告从计划开始，而不是从一个空文件开始。它之所以存在，是因为它服务的那个阶段**从未留下过一件存活的产物**：作者工作区里十七份已交付计划，六份声称 `verification_status: verified`，其中**四份的报告指针指向已不存在的文件**——有两份指向会话临时目录，会话一结束就被删除——而那些页面不带「未经事实核验」横幅，于是旅行者读到的是一个谁也无法核查的权威。这不是偷懒：报告是本 skill 要求的两份文档里更难的那一份（七个块、档位由计划自身字段算出而非作者选择、还有一条要求「每张声称查过营业时间的餐厅卡片都必须被 pointer 点名」的覆盖规则），而唯一的向导是「猜错之后闸门告诉你哪里错」。脚手架把报告绑定到计划、算出档位、并预填每一个 pointer——写出前逐一验证过能解析。每条结论都以 `TODO:` 产出，因为给证据文档做脚手架离「假证据生成器」只差一步；`check_verification` 现在会拒收仍带占位文本的报告，所以填不完就交付不出去。随后 `save_trip_deliverables.py` 会把报告复制到计划旁边并作为第四条路径报出，`audit_workspace.py` 也会点名任何证据已丢失的已存计划。

**`intake_language.py`** 决定两张填写表单说哪种语言。两张页面都带一份中英词典和一个切换按钮，切换的只是文字：存下来的每个值在两种语言下完全一样。页面在给了 `--language` 时用它；否则用已存档案里的「希望输出语言」（旅行者自己的写法，比如「中文」「English」，在这里统一换算，「中文和 English」这种双语答案不对应单一语言；`en_US` 这类语言标签和 "Simplified Chinese" 这类语言名称也能识别，因为在对话里写出来的档案会这么写）；再否则用填写档案时页面用的语言（档案服务会记在 `identity_and_language.profile_form_language`）；再否则用中文。第一次使用的旅行者，行程表单跟随他们刚保存的那份档案。每张页面提交时都会带上自己当前的语言，所以切换过语言的旅行者收到的回复就是屏幕上的语言；存下来的 intake 会记录 `form_language` 和 `preferred_output_language`，`new_plan_skeleton.py --from-intake` 据此决定计划的语言（命令行的 `--language` 仍然优先；旧到没有这两个字段的 intake 会被明确报告出来）。2026-09-24 之前，这个偏好收集了、传给了行程表单，然后就丢了：15 份真实 intake 里一份都没有带上它。

**`verification_sections.py`** 把一次核验绑定到它读过的内容上。带核验保存时，会往计划里盖一份 `verification_receipt`：按段落记录指纹——每天按日期、每张预订卡按 id、其余内容块按名字，脚本自己写的字段一律不算。2026-09-24 之前，报告只按文件名和日期绑定计划，于是核验之后把某天 13:30 改成 14:00，照样能以「已核验」保存、页面不带横幅。现在用同一份报告再次保存时，闸门会点名改动过的段落，只有报告里为每一段的当前版本都追加了一条 `rechecks` 记录，`check_verification` 才放行——每条记录会写下它复核的那个版本的指纹，所以同一天再改一次，就需要一条新的复核记录；`new_verification_report.py --recheck` 会把这些记录（连同指纹）以 TODO 的形式写好。用 `--overwrite` 覆盖已交付的副本时，保存会拿那份副本里的回执来比对，因为作者手里那份工作文件从来不会被写入回执。之所以按段而不是按整份文件：旅行者只换一家餐厅，不该为此重买一整轮七个块的核验。每段的指纹还包含它核验时依据的行程事实——人数计入每一天、每张预订卡、预算和交通总览；旅行者限制计入每一天、每张预订卡和交通总览——因为曾有一次同行人数从四人变成五人，只复核了 `trip` 一段就以「已核验」保存，所有酒店卡片仍是四人间。指纹带 `v2:` 前缀；此前盖的回执是不带前缀的旧指纹，按它当时的算法比对。这个模块还负责把复核流程的下一步生成成可以原样运行的命令（当前解释器、绝对路径、带引号）：保存被拒时打印复核脚手架命令，脚手架就地修改报告并打印接下来的保存命令。复制到已交付方案旁边的报告会改写成指向那份方案；回执出现之前就交付的副本会被拒绝而不是重新认证，因为没有任何记录说明它的报告核验过哪些内容。

**计划必须回答「落地第一小时」。** `arrival_essentials` 是一个必填块，含四条——`payment`（怎么付钱）、`connectivity`（怎么上网）、`emergency`（出事找谁）、`health_and_insurance`（医疗与保险）。它之所以存在，是因为契约里其他每一块讲的都是**那几天**，没有一块回答旅行者走出到达大厅时真正会问的问题：我能刷卡吗、我能上网吗、出事打给谁、我有保险吗。一个页面把六天的饭都排好了，却说不出旅行者兜里那张卡能不能在第一台售票机上刷过去，它只回答了容易的那一半。每一条要么是 `researched`（带摘要、HTTPS 来源和核查日期），要么是 `unverified`（带摘要，并如实说明没核过），要么是 `not_applicable` **并给出理由**——国内行程不需要领事馆，而「说出这一点」和「根本没人去看」是两回事。一条 `researched` 的 emergency 却不写当地急救号码，会被直接拒收：那是这一块里唯一一个「出事当下真的有人去拨」的字段。这些恰恰是最容易凭记忆作答、而且答错的事实——逼出这一块的真实案例是：中国护照、荷兰居留，飞瑞士。荷兰的 EHIC 在欧盟通行，**对他却在瑞士完全无效**，因为欧盟把第三国国民纳入社保协调的条例不适用于瑞士。区分这两个答案的只有国籍一项，而原先计划里没有任何东西会去问。脚手架会带 `TODO:` 标记把这一块写出来，让它以「一张待填的表」而不是「一次闸门报错」的形式出现；渲染器把它印成独立面板；页面闸门要求 `#arrival-essentials` 这个区块必须存在——**收集了却不展示，和从没收集是同一种缺陷**。

**`check_plan_contract.py`** 在闸门之前、一次针对整个文件，回答闸门刻意不回答的那个问题：这份方案里的每个键，`templates/final-trip-plan.json` 都认识吗？闸门按主题校验、遇到第一个不过的类别就短路——这对闸门是对的，对作者却很贵：一次实测的 Construction 运行光在字段名上就花掉**十三次串行往返**（`duration_minutes` 写成 `total_duration_minutes`、`search_url` 写成 `url`、`per_person_low` 写成 `amount_low`、该是六个字段的 `outbound_itinerary` 写成了一句话），而只要有东西一次点名这十三个，一次编辑就能全改完。它不需要网络，每个未知键旁边给出契约里最相近的那个名字，按路径去重（同一个错跨六天只报一行），契约里是空数组的字段内部一律视为作者自己的事而非拼写错误。它是一份待办清单，不是判决：它分不清拼写错误和你有意加的字段，它对方案是否属实一无所知，**它不报错不等于通过**。拿作者工作区里所有方案跑一遍，它还翻出八个渲染器和闸门都不读的字段名——契约里叫 `dietary_or_religious_needs` 却被写成 `dietary_needs`、该是列表的 `excluded_places_checked` 被写成了 `true`——它们正是因为没人读才活到了今天。

**`check_plan_consistency.py`** 把「散文靠不住」的部分交给代码判定：路线合计必须由自身 segment 求和、步行数字必须从数据推导而非手写断言、每顿饭必须挂在当天路线的真实站点上且落在营业时间内、日历不得有缺口、预算合计必须等于它声称求和的那些行且声称包含的每个类别都真的有明细。

**两个闸门现在都有两种报告形式，第二种是写给模型看的。**散文报告说的是「哪里**错了**」，然后把「错在**哪个字段**」留给作者自己去翻计划 —— 而计划正是这个循环里最大的那个文件，每修一轮就要重读一次。`--json` 打印 `{ok, findings:[{rule_id, pointer, message}], rules:{rule_id: 该规则本身的措辞，只出现一次}, notes}`，走 stdout，退出码不变，且**每一个出口都会打印一份 JSON**（包括读计划之前就拒绝掉的那些），所以外层脚本可以把这个 flag 加在每一次调用上，连失败的那一次也解析得动。有两条性质让它真正能用，而不只是「机器可读」。第一，它是**无损的**：`message` 接上它自己那条 `rules[rule_id]`，逐字节就是散文里的那一行 —— 这一点是这样验的：把作者工作区全部 15 份计划的 JSON 逐条还原回散文行，再和上一个提交在同样 15 份计划上的输出对比，两边都是 928 条发现，且没有任何一份计划的发现**集合**出现差异。第二，每条发现都带一个**打印之前已经解析过的 pointer** —— 计划闸门给的是计划内的路径 `days[0].dining[1].venue_hours`，页面闸门给的是它刚读过那份页面里的 `line N col M` —— 于是「修一条发现」变成「在指名的位置改一处」，而不是再搜一遍。解析不到的候选位置会被丢掉，而不是照样印出来：指错位置的代价和它本想省掉的那次重读一样大，而且作者被指错一次之后，就再也不会信这个字段了。所以 `null` 的含义是**这个闸门定位不到它**，绝不是**这个字段不存在**：那 928 条计划发现里有 846 条带 pointer，124 条页面发现里有 89 条带 pointer；剩下的那些，要么是针对整份计划的发现，要么它唯一的抓手是一个在计划里出现不止一处的值（闸门宁可不指，也不在两处之间瞎猜），要么是页面上「该有的标记压根不在」这类发现 —— 不存在的东西没有行号。这个 flag **不会**让报告变小：在同样这 15 份计划上，JSON 是 245,062 字节，散文是 174,064 字节。它省掉的是另一笔账 —— 作者不必再打开那份计划。

散文那一半也做了对应的处理。以前一条规则命中多少次，它的整段理由就重印多少次；现在重复规则的**第一条**发现带完整措辞、结尾标 `[rule R1, stated here]`，后面每一条只印它自己特有的部分、结尾标 `[rule R1, stated above]`，块首另有一行图例解释这两个标记。在同样这 15 份计划上，这让计划闸门的输出从 354,118 字节降到 174,064 字节，而发现集合一条不差。这只发生在 `check_plan_consistency.py` 上：`validate_trip_html.py` 的发现本来就是一两句话、没有可压缩的重复理由，它的散文输出和上一个提交在工作区那 12 份「旁边有计划」的页面上逐字节相同 —— 页面闸门的规则 id 与出处引用，是在它自己的 `--json` 里才只说一次的。这套机制还会在「打标记加图例反而比省下的尾巴更贵」的报告上**自己关掉**：一种可能把输出变大的「节省」，是没人能推理的节省。

2.0 的一次自审又找出它自己的三个盲区：行程日期反转（会让日期覆盖循环一次都不迭代，从而**静默关掉下游全部日期检查**）、负数路段（−25 分钟的一段能抵消真实的一段，算术却仍自洽）、以及某天声称的换乘次数少于它自己各路段声明之和。

**2.1 补上的是一位旅客用鼠标点出来的三个缺陷——而在他点开之前，上面每一道闸门都是绿的。** 一份已交付的方案把自己的中文显示标签直接写进了地图 URL：`origin=酒店（拉斯坎特拉斯海滨）`——「酒店」这个普通名词加一句描述——被 Google 解析到了**台湾**，给出一条 65 小时的驾车路线。那份方案 15 个端点里有 6 个根本无法地理编码，而 `check_link_targets.py` 报告 25 条地图链接**全部 ok**，因为主机名对、状态码是 200。它的餐饮卡完全没有质量信号，于是一家在所有平台都查无此店的餐厅进了晚餐，两家 20:00 才开门的餐厅进了午餐。它的两家酒店共用一条字节完全相同的 Booking.com **城市**搜索链接，没有任何按钮能打开具体那一家——也就没人发现其中一家 7 晚 €1,256、光住宿就超过全部预算上限，而另一家在那些日期上根本没有空房。

- **`check_map_endpoints`** —— 地图 URL 的参数是地理编码查询，不是标题。端点必须是坐标；自由文本一律拒绝，因为地名有时能解析、有时会落到另一个大陆，而离线检查分辨不了这两者。`trip.destination_coords` 只需声明一次，却让每个端点从**相对**校验变成**绝对**校验：单靠「两端距离不超过该段声明距离」是相对的，把拉斯帕尔马斯某段两端都写成 `lon,lat`，两点仍相距 4.73 公里（正确值 4.70），而所有针位已移到非洲南部。它还会拒绝带途经点的公交 URL（Google 对这种请求根本不返回路线）、超过 15 公里的「步行」按钮，以及声称 `multi_stop` 却跳过当天中间站点的链接。
- **`check_venue_quality`** —— 每张餐饮卡都必须带评分及其分制、评价数与来源，或者明说「没有评分」并给出理由。卡片不得一边声称营业时间未核实、一边排出具体用餐时段：把一顿饭放上时钟，**本身就是**在断言那家店当时开门。它的门店链接必须以店名或 POI id 为键，而不是一句描述。
- **`check_booking_identity`** —— 比价链接必须限定到具体商品，让按钮打开那一家而不是一份列表。店名比对采用双向折叠后取子串，因为只认拉丁字符的切词器对「东京银座三井花园酒店」返回空，等于静默豁免了全部中日文市场。两个「候选」若打开同一个页面，那就是同一个选项展示了两次——这个缺陷在机票上和酒店上都发生过。

这三条随后不是被欣赏、而是被攻击了一遍；结果第一条的初版**并没有拦住它被写出来要拦的那个缺陷**：把已交付方案换回原来的中文标签、只改一行让任何一天都不再声称 `multi_stop`，检查器就退出 0。`tests/test_plan_consistency.py` 的第 23–27 节把全部 13 个攻击向量逐一钉死。

**2.2 继续攻击，而这次找到的东西大多在门禁自己身上。** 坐标解码器按数值范围去猜 `lat,lon` 还是 `lon,lat`，结果恰好搞坏了本技能强制使用非 Google 提供方的那个市场：北京因经度大于 90 而侥幸正常，乌鲁木齐按高德文档顺序正确书写却被读成纬度 87.6、判定为在 4,946 公里外的北冰洋——而作者若照错误信息去「检查坐标顺序」，会得到一个全绿的门禁和一堆指向北冰洋的按钮。两处评分下限都印着一个**没有任何代码会读**的出口（「或在 why_this_stop 里说明理由」），于是老老实实写理由的人被拒，而把 `rating_status` 翻成 `"none"`、低分原样留着的人直接通过。`_fold` 被写成白名单**两次**：第一版只认拉丁字母，第二版补上中日韩，却静默豁免了西里尔、希腊、泰、阿拉伯、希伯来与天城文。另外 2,500 公里的锚点半径会拒绝「纽约+洛杉矶」，3 倍绕行比会拒绝科罗拉多大峡谷南北缘——直线 18 公里、驾车 350 公里。

还有两条来得最有价值：有人打开页面看见了。整段话被印成 `这 · 是 · 路 · 线 · 概 · 览`——每个字都被点号隔开——因为 `transport_overview.notes` 是字符串**列表**，被写成了一个字符串，而渲染器要 join 它：遍历一个 `str` 得到的是单个字符。所有门禁都放行了，因为那个值是完全合法的字符串、那行 join 是完全合法的代码，**没有任何一处检查类型**。而由此新增的检查一开到已交付的计划上，又炸出 54 处一直在原样打印星号的 `**加粗**`，外加一句在路段已改为 35 分钟之后仍写着「约 25 分钟」的话。

本版新增四项检查——`check_implied_speed`、`check_list_typed_fields`、`check_prose_rendering`、`check_prose_agrees_with_data`——使 `PLAN_CHECKS` 从 14 项增至 18 项；测试套件第 28–37 节把上述每一条都从**两个方向**钉死，因为通过这类规则最省事的办法，就是让它永远不响。

**2.3 是第一个由语言而非点击发现的版本。** 其中每个缺陷都需要计划语言与条目文字不同才会出现，英文行程根本碰不到。防止锚点回落到目的地自身条目的守卫跨文字系统比较 token——同一座城市，`{"larnaca"}` 不可能是 `{"拉纳卡"}` 的子集——于是它放行了一切：中文计划里的「拉纳卡市政市场」吃到了 *Larnaca* 条目，配图是芬尼库德斯海滨步道，一个完全不同的地方，挂在市场的标题下。而用剥离停用词的分词器去修，又把拉纳卡中世纪城堡误杀了——`castle`、`church`、`museum`、`market`、`beach` 全是停用词，任何「<城市> <类型>」条目都会塌缩成光秃秃的城市名。与此同时，一趟休闲行程的封面图是机场航站楼，而且是被「升级」选出来的：Quality Image 流程用一个「城市名在前、航站楼在后」的文件替换掉了条目原本的题图。

本版三个缺陷里有两个是修前两个时引入的，这部分才值得读。最直观的封面规则——文件名不得引入任何其他词——会连带拒绝这套启发式本就该接受的 `Vista de Alicante, España`，等于对所有目的地关掉升级功能：用特性换掉了缺陷。现在只有具名设施才会取消封面资格。预算图表在渲染器里是同一种形状的错：图例印着 `local_transport 54`，正下方的表格行却是「市内交通: €47–62」；而**那个**的第一版修复又改写了图表之外的作者正文——同一句话翻译了两项、留下第三项，只因为前两项后面跟了分号。三个闭包被提升为模块级函数，让新测试检验规则本身而不是规则的副本；六次回退各自都会让测试变红——其中一次在第一轮存活了下来，因为那些检查手工构造了输入，从未调用过修复真正所在的那个函数。

**2.4 是那些「好言相劝」的规则开始真正失败的版本。** 起点是一份反馈：换一个 agent 跑，它直接转成聊天提问，最后产出的页面丢掉了一半要求。顺着查下去，背后每个缺陷都是同一个形状——规则只写在散文里，或者闸门要两样东西却只读了一样。`--assistant auto` 靠**名字**识别「已经有助手在驱动」——`CLAUDECODE`、`CLAUDE_CODE`、`CODEX_THREAD_ID`——其余一律当成裸终端，于是在 Gemini CLI、Cursor、Copilot CLI 或自建 SDK agent 里，它会在正在规划这趟旅行的助手背后再起一个脱离的规划器：正是它自己注释里记录的那次事故，被那次事故的修复重新引入。助手名单只在写下它的那天是全的；「有没有人打开这个终端」不会过期。同样是那些 harness，把「Default to the local HTML intake workflow」读成了偏好，所以计划现在必须携带 `intake_context`——`html_form` / `user_supplied` / `chat_fallback`，各自带上自己的证据，走聊天时带的是旅行者**本人**拒绝表单的原话。

找出其余缺陷的那个测量方法，比其中任何一个修复都更值钱：把契约里的字段换成唯一标记，跑完整的落盘流水线，再去产出的 HTML 里 grep 它。`avoid_list`、每一条 `avoid_list_handling.how_avoided`、以及自然与人文子类型，全都存在于计划 JSON 里，到达页面的次数是**零**——而 `check_plan_consistency.py` 却**强制要求**每条 avoid 都配一条处理说明。闸门逼着你回答，而答案从不给旅行者看，这正是本 skill 关于评分的那条规则，落在了「为什么要去这一趟」的那一半上。同一轮扫描还发现：声明了的步行上限，只对老实填数字的计划有效——`max_continuous_walking_minutes=20`、活动什么都不声明时，计划干净落盘，页面写着「20 min」；而同一份计划如实写上实际步行的 180 分钟，反而被拒。沉默被奖励，数字被惩罚，对象恰恰是这条规则要保护的那个人。现在有上限就必须**给出声明**——音乐会写 0 是个合格答案，什么都不写不是。

同一家族还有四个：`1970-01-01`，骨架为它无法得知的日期留的占位符，会作为「已核实」的 `checked_at` 出厂，页面照旧在旁边印着「已核实」；门票的 `day_number` 只校验它**存在于**计划的日期里，而不校验它和使用它的那个活动是否同一天——于是东京那次「时效性门票指向错的晚上」在它自己的修复之后依然活着，因为存在不等于一致；`check_shortlist_consistency.py` 在没有 `--intake` 时退出码是 0，而助手读的就是退出码；还有 `candidate.evidence` 从来没被任何代码读过，所以一个目的地可以拿 82 分、被点名为胜出者、推荐给旅行者，而底下的证据列表是空的。在 `replan_trip.py` 之后，`resolved is True` 会在任何东西看 `resolution` 之前直接短路——把所有标记翻成 true，就能把「为周一研究、如今已是周四」的营业时间原样出厂，而闸门报告「全部已解决」。

有两件事这个版本**没有**改，而它们同样是结论。核验报告那道闸门扛住了 11 次伪造与陈旧攻击——删掉一个 domain、移除两个审计员、`claims_checked` 退回数字、指针无法解析、`wrong` 结论未解决、报告声称查的是另一份计划、报告日期早于它声称检查的计划——什么都不用改。另外，第一轮里有好几个「缺陷」被撤回了：金丝雀写在了契约根本没有的字段名上（`sources[0].title`、`activity.why_it_fits`、`segment.fallback`），读起来和「这个字段从不渲染」一模一样。**先证明改动真的落进去了，再相信闸门的沉默。**

**2.5 是这个 skill 终于被完整跑了一遍、而旅行者发现了所有闸门都发现不了的东西的版本。** 一份真实的六天行程被建出来、过了全部闸门、交付出去；旅行者读完页面提了四个问题。其中三个底下是同一个形状——**计划关于它自己的说法，从来没有和它所描述的东西比对过**。页面一张照片都没有，是因为一个为拉丁文字调的三字符 token 下限（在那里它只排除 `the` 和 `and`）抹掉了所有双字 CJK 名字：`_tokens("香港")` 返回空集，于是香港、北京、上海、东京、京都、台北、澳门的封面图全部无法解析——在每一份中文计划上，静默发生，而运行照样退出 0。机票按钮打开的是一个空搜索框，**而计划正声明这不可能发生**：它声明出发地、目的地、两个日期和人数都已预填，实际却把它们塞在自由文本 `?q=` 的一句话里，闸门用子串检查了五项中的两项，另外三项根本没找过。计划关于自己声明的字段是一种**自证**，而自证只记录规则被「声称」过，从不记录它被遵守过——所以凡是能直接问产物的地方，现在就直接问产物。还有一整类证据在同一份计划里被两次判死刑，而两次都只探了**列表页**，真正带营业时间、决定旅行者会不会站在关着的门前的是详情页；`probe_sources.py` 只报可达性，并且明说可达 ≠ 可取。

同一次运行也量出了闸门让作者付出的代价。它十三次迭代根本与这趟旅行无关——全是字段名，`search_url` 写成 `url`、`per_person_low` 写成 `amount_low`、该是六个字段的 `outbound_itinerary` 写成了一句话——每一个都花掉一整个周期，因为闸门按主题校验、遇到第一个不过的类别就短路。这对闸门是对的，对作者很贵，所以 `check_plan_contract.py` 回答闸门刻意不回答的那个问题：这里每个键，契约认不认识？它在闸门之前一次全报，并给出最相近的正名。拿整个工作区跑一遍，它还翻出八个**没有任何东西会读**的字段名——契约里叫 `dietary_or_religious_needs` 却写成 `dietary_needs`、该是列表的 `excluded_places_checked` 写成了 `true`——没人读，正是它们能活着交付出去的原因。

还有两处缺席，是结构性的而非 bug。Discovery 拥有本 skill 第二大的闸门，却**没有门**：一个存着十五份 intake 的工作区里，短名单文件数是零，所以那道闸门拒绝的一切，从来没有被拒绝过。它现在有门了，并且和这里其他一切一样带 `--intake`/`--no-intake` 二选一，因为一个「不说话就能跳过」的检查，在催生它的那次运行上一定报干净。而 intake 表单——五十多个字段、多条条件分支、旅行者所有回答进入流水线的唯一入口——**一个测试都没有**。现在有了，用从它自己 markup 建出的 DOM 跑它自己的 JavaScript；写测试的当场就抓到一个一小时前的缺陷：一个联动被加在了表单自身 IIFE 的外面，那里 `$` 根本不存在，所以它控制的面板永远不会出现。语法完美、作用域错误、仓库里每道闸门全绿。

**2.6 是这个 skill 第一次为「会移动的行程」运行的版本。** 在它之前，一切都默认只有一个目的地，而这个默认在计划睡到第三个地方之前是看不见的。一位旅行者要从阿姆斯特丹去蒙特勒、伯尔尼和琉森，六天，这个形状打破了五条规则——每一条对「待在原地」的行程都曾经是对的。计划本来就能表达这个序列（每站一个 `stay_group_id`、城际段带车站与日期、`transfer` 日型、当天路线承载移动），作者工作区里已交付的一份计划甚至全都写对了。**只是没有任何东西把它渲染出来**，页面印着一个 `trip.destination` 字符串，读者得自己看完四张日卡才拼得出这趟在移动。

失效的每条规则都只有一句话，而每条都有真实代价。**「至少两个可比选项」是按类别数的**，于是北京→上海和上海→北京成了同一程的两个选项：数量通过、`review_url` 不同所以唯一性也通过，而两条腿一个都没被比较过——腿越多，闸门越自信地报告一个不存在的比较。**`entry_context` 全程只答一次**，于是泰国→越南→柬埔寨的计划可以只带泰国那份、引用泰国官方来源、通过全部闸门，然后在页面上印「免签」——对其中两国是错的；答错入境是登机被拒，不是餐厅关门。**高德规则是整页级的，而服务市场是逐站的**，于是深圳+香港的计划被告知香港那两天必须用高德——那不是香港公交适用的工具——旅行者只能二选一：半程拿到不能用的链接，或者整份交付不出去。**`ground_transport` 要求每张卡片都有回程日期**，于是链式行程的单程段没有任何诚实的形状：要么把两段单程谎称成往返，要么删掉卡片、让铁路行程上最大且最赶时间的那笔购买无处可买。还有**铁路搜索按钮要求预填乘客数**，而 SBB 官方深链接根本没有这个参数。

**计划里的路径是一个请求，不是一条指令。** 有两处会从计划 JSON 里取出文件路径并打开它。这件事之所以要紧，是因为本仓库把计划当作**可携带文档**——会被重渲染、重规划、从搬过家的工作区里审计——而会流动的文档就可能来自别人。intake 那条给出的是文件存在性探测，外加任何带 `experience.ranked_must_haves` 的 JSON 的字符串；配图 sidecar 那条更严重，而且促成这轮工作的那份审计**没有发现它**——它的字节会被解码成 `data:` URI **嵌进交付页面**，所以任何可读且能解析成图片槽的文件，都会随着旅行者分享的产物离开这台机器。

**锚点的照片必须是锚点本身，不是包含它的那个地方。** 同一个缺陷的第三次——前两次是机场顶替城市、城镇顶替它的市政市场——而这是第一次靠 token 比较无法判定：「Château de Chillon」/「Chillon Castle」与「Marché de Vevey」/「Vevey railway station」结构完全一样，要分开必须知道 *château* 等于 castle 而 *marché* 不等于 railway station。维基百科自己的简短描述带着主体类别，而且能搭在模块本来就要发的那次请求上。

**还有：闸门通过时保持沉默，原来是最危险的时刻。** 这一条是拿另一个助手实测出来的，不是推理出来的：给 codex 一份带三处缺陷的计划和一句指令。它跑了两道闸门、把两道报出的都修好、看到两个干净的退出、然后报告计划已修复——而第三处缺陷还在，因为抓它的规则在第三个命令里，而它从没跑到那一步，也没有任何输出告诉它还有第三个命令。装不下这份文件的助手，是靠上一条命令的输出重建流程顺序的。现在每道闸门在成功时都会说出下一条命令；同一个 agent、同样的缺陷、同样的提示词，再跑一次，零残留。

**核验阶段**（[`references/verification.md`](../references/verification.md)）负责只有真实世界能回答的部分：入境规则、票价与时刻、营业时间、该日期是否已开售、季节性事实。它拆成五个真实性域，外加两个完全不联网的审计员；因为让**一次**调用同时查完这么多事，每件只能分到很小一部分注意力 —— 那正是晚餐被排进已打烊餐厅的成因。运行时支持并发就并发；不支持就跑五趟**各自独立**的串行，而不是塞进一个 prompt。收益是注意力集中，不是墙钟时间。闸门拒收「缺了这份计划所在档位要求的任一个块」的报告 —— 完整档位七个块，轻量档位四个（`sights_and_hours`、`transport` 与两个审计员），档位由 `check_plan_consistency.py` 读计划本身算出，而不是由谁声明。交足七个块永远不会被拒，所以档位只会把下限往下调。两个审计员在任何档位都是必需的：在促成这条规则的那次运行里，这两个最便宜的 agent 找出了 55 个缺陷中的 27 个。

**`plan_slice.py`** 交给每个核验 agent 的，是计划的一份**投影**，而不是计划本身。`references/verification.md` 原来写的是「每个核验 agent 拿到计划路径」，于是五个真实性域把同一个文件读五遍 —— 而 2026-08-30 在一个真实工作区的 15 份计划上实测，这个文件从 28,943 字节到 2,132,252 字节、中位数 85,836，对应的是 `references/research-budget.md` 给这一轮定价的 ≈700k tokens。想当然的做法是错的，而错在哪里值得留下来：按表格里每个域那一行去做**白名单**，会把 `days` 从 `booking_and_lodging` 手里拿走 —— 而它要回答的正是「票开售的那一刻旅客人在哪里」；也会把航班卡从 `entry` 手里拿走 —— 而中转机场的过境签恰恰写在那里。所以这份切片是**减法**的：`trip`、`days`、`budget` 无条件保留；只有当某个块里没有任何字段能回答该域那一行时，才把它删掉；脚本没见过的顶层键一律保留并明确报出来 —— 白名单会在 schema 一长大就把某个域饿着，而黑名单最多只是省得少一点。它只按顶层键切、别的一律不动，所以指向保留块的每一个 `claims_checked` 指针，在真实计划上仍然解析得到 —— 那正是 `check_plan_consistency.py` 要检查的东西。省下来的量如实报告，不粉饰：在全部 15 份计划 × 5 个域上实测，中位数那份计划的切片小了 3.3%–7.4%；唯一一份把 `imagery` 内嵌在计划里的，小了约 96%；而 **75 份切片里有 13 份比计划本身还大**（最小的两份计划上五个域全中，另有两份计划各中一两个域） —— 工具会原话这么说，于是答案是「这个域直接给计划路径」，而不是一份谁也没拿到的节省。`booking_options` 与 `sources` 被五个域全部保留，依据同样是实测：那 15 份计划里有 3 份把日落/白天时长写在了 `booking_options` 里，其中两次就在航班卡上、还是「为什么选这班而不是那班」的理由本身。两个审计员按名字直接拒绝 —— `consistency` 与 `completeness` 比的是计划的两个部分之间，从文件里删掉一个块，和这份计划本来就没有这个块，看起来一模一样。切片写在计划旁边的 `slices/` 里，而不是写进 `plans/`：`audit_workspace.py` 是按**形状**认计划的 —— 有 `days` 列表、有 `trip` 键，而每一份切片都满足 —— 并且用的是不递归的 glob；切片要是落在 `plans/` 里，每趟行程就凭空多出五份「计划」，之后每次审计都会把它们当行程审、报它们缺了本来就不该有的块。

## 其余工具

**`new_plan_skeleton.py`** 生成一份结构合法、等着填内容的方案骨架。模板列得出每个字段，却表达不了字段之间的规则，这些以前只能靠撞失败去学 —— 一次实测为此损失了三轮返工和 21 个结构错误。所有待填值都是 `TODO:` 标记，`validate_trip_html.py` 拒绝含 TODO 的页面，所以「起步更快」不会变成「能交空壳」。

有两个字段装不下 `TODO:` 标记，漏洞就在这里。`allergy_severity` 和 `max_continuous_walking_minutes` 是**有类型的** —— 一个是闭合枚举，一个是数字或 null —— 往里写散文，骨架根本通不过校验；而脚本改写进去的那两个值（`"none"` 和 `null`）读起来就像旅行者的回答，可根本没人问过。它们恰恰又是餐饮闸门和步行闸门真正**拿来测量**的两个字段：拿工作区里一份真实的五天计划实测，在它已填的上限 25 之下删掉每个活动的 `on_foot_minutes`，`check_walking_budget` 报出 5 条；把上限改成 null 再做同样的删除，报出 0 条。所以骨架会在它们旁边写下 **`trip.traveler_constraints.untyped_constraints`**，每个没人填过的字段一条，这正是「这位旅行者没有步行上限」和「根本没人问过」之间的全部差别。只要还剩一条，`check_plan_consistency.py` 就点名拒收这份计划，每日步行提示不再把 null 上限说成旅行者的回答，轻量核查档位也不予发放 —— 没填的约束是一个悬着的问题，绝不是一张健康证明。字段填好了就删掉对应那条；`{}`、`[]`、`""`、`false`、`0` 都读作「没有未填项」，而 `true` 或一个光秃秃的数字会被拒绝，因为它和「本想列出待填字段却没列」分不出来。`templates/final-trip-plan.json` 里带着这个键、值是空标记，正是这个空标记，让旁边那句 `allergy_severity: "none"` 成为一个确实有人给出的回答。

**`check_link_targets.py`** 逐个跟踪外链按钮，报告它实际落在哪里。**故意没有**接进 `save_trip_deliverables.py`：它需要联网，而一道会在飞机上或 CI 里失败的闸门最终只会被绕过。`broken` 判定刻意收得很窄 —— 只有硬 4xx/5xx 和跳转到不同域名。其余归为 `unverified`，因为服务商的回答取决于是谁在问：同一个 Google Flights 地址对浏览器返回 200 不跳转，对脚本却跳到 `unsupported` —— 这个检查的早期版本正因此错判过一条完好的链接。

`save_trip_deliverables.py` 还会拒绝保存**不肯说明需求是怎么收集来的**计划。`intake_context.method` 取 `html_form` / `user_supplied` / `chat_fallback` 三者之一，且各自必须带上自己的证据：表单服务端写下的那个意向文件、旅行者另行提供了什么的说明、或旅行者**本人拒绝表单的原话**加日期。没有逃生开关 —— 这三条已经覆盖了全部正当路径，被拒的只是「不肯说走的是哪条」。它之所以存在：这条规则以前只是散文（「默认走 HTML 表单」），而实测下来，别的 harness 上的助手把「默认」读成了偏好，一个表单都没打开就直接转聊天提问。那样会丢掉表单服务端对证件/支付/地址字段的拒绝、目的地范围与工作模式的矛盾校验、档案里 `never_recommend` 与忌口的预填，以及 `check_shortlist_consistency.py --intake` 用来计算硬约束清单的那份意向文件。散文不会让一次运行失败，这道闸门会。

**买不到的票不算票。** 歌舞伎座一幕見席在前一天 12:00 开售，而计划自己的时间线在那一刻把旅行者放在成田入境队列里——它自己的时间线反驳了它自己的指令，而没有任何东西去比对这两者，因为开售时刻根本不是数据。加这个字段是个**决策**而不是补丁：设成**可选**就会是这个 skill 反复出现的那个缺陷又一次——没研究过开售窗口的 agent，正是会省略这个字段的那一个；而设成必填却放任自由填写，又会诱发条件反射式的 `always_available`，那是**编造的事实**，比一个可见的空白更糟。所以它只对某一天真正排上的票必填，且每个值都欠一句 `basis` 说明规则从哪来——真开过官网的人写得出来，猜的人写不出来。闸门随后拿开售时刻去比计划自己的每一天，并且刻意对两种情况保持沉默：旅行者在场时开售，以及出发前就买好这种最常见的情形。

**页面自己会说闸门跑没跑过。** 这里每一道检查都是脚本，而脚本只有被调用时才会运行——一份手写的页面绕过全部检查，而且和落盘产物看不出区别。脚本内部解决不了这件事，因为执行点在它们的上游。页面**能**做的是携带证据：闸门印章此前只写进 plan JSON 就停下了，而这正是本仓库当初为「未经事实核验」横幅解决过的同一个缺口——理由是，只存在 JSON 里的标记，永远到不了在航司柜台前举着行程单的那个人手上。现在落盘页面会带上 `data-gates-checks`，并在来源登记区渲染出一行可见文字——而那行文字明确写出这个印章**不**代表什么，因为把二十来道结构检查读成「已核实事实」，比没有印章更糟。印章记的是**数量**而不是清单 —— `gates_stamp()` 返回 `len(PLAN_CHECKS)`，今天实测是 `{'checks': 24, 'checked_by': 'check_plan_consistency.PLAN_CHECKS'}` —— 所以这里刻意不写死一个字面数字：这句话在计数悄悄变成 24 之后，仍然写着 **22**，凡是文档手抄一遍的数字，只要有人加一道检查就会过期。任何缺少印章的页面，`validate_trip_html.py` 都会打一条 note。

`save_trip_deliverables.py` 没有核验报告就拒绝保存。`--unverified` 逃生口保留 —— 一道被绕开的闸门谁也警告不到 —— 但它的代价从「沉默」变成「可见」：落盘计划记录 `verification_status: unverified`，页面最上方渲染一条随语言本地化的**「未经事实核验」**横幅。

**`check_shortlist_consistency.py`** 是 Discovery 模式有史以来第一道闸门。Construction 有十九项检查加一个 HTML 校验器，而候选评估契约只在 SKILL.md 的散文里被提到、没有任何脚本读过它——关于可比性和硬过滤次序的所有规则都活在句子里。候选集是一次**比较**，它最严重的缺陷长在**候选与候选之间**：每份记录都可以无懈可击，而排名毫无意义——一个按人头计价的数字旁边放着一个按全团计价的，或者一个只含机票的旁边放着一个全包的。旅行者挑了那个更小的数字，而它根本不是更便宜的那趟行程。各种到达方式被折叠成同一个成本面，所以坐火车到的候选可以和飞过去的候选直接比、双方都不必额外声明——这正是杀掉规则初稿的那个误报。它只判定集合运算和算术能判定的事，从不判断证据是否充分、分数是否配得上。

**`save_discovery_deliverables.py`** 是那道闸门一直缺的门。Construction 那边的对应脚本会打印 `Plan JSON:` 和 `Final HTML:`，这两行是闸门跑过的唯一外部标志 —— 所以缺了它们的计划不算完成的任务。Discovery 有闸门却没有门：命令埋在段落里，输出文件没人规定该放哪，而跳过这两件事的运行，和两件都做了的运行长得一模一样。在一个存着十五份 intake 的真实工作区上实测，shortlist 文件数是零 —— 这道闸门拒绝的一切，从来没有被拒绝过。本脚本把 shortlist 送过闸门、把跑了什么盖进文件（包括约束检查到底有没有上膛）、写到旅行者其它产物旁边，并打印 `Shortlist JSON:`。`--intake` 或 `--no-intake` 二选一必填，和 `--verification` / `--unverified` 是同一对形状、同一个理由。没有 HTML：旅行者是拿着手机站在陌生城市里照着计划订东西的，而 shortlist 是对话里读一次的决策辅助 —— 存下的 JSON 是「这份比较被检验过」的记录，不是第二份要读的东西。

加上 `--intake`，它会从旅行者真正填过的表单里**计算**出硬约束清单，然后要求每个候选逐条作答。是计算而不是让作者手写：手写进候选集的清单可以少列——作者列出自己记得应用的那四条，每个候选都覆盖了那四条，于是门禁恰好在催生它的那次运行上报告「覆盖完整」。其余规则关于**结论本身**：`outcome.state` 是必填的，因为「没跑完的过滤」和「真实的约束冲突」会产生同样的空通过集，而只有其中一种配得上让旅行者放弃一项真实需求。已声明的冲突不得与幸存者共存、必须点名该放松什么、也不得声称一条其实只淘汰了部分候选的约束——旅行者不该为一条只淘汰掉一个候选的阻碍去改掉两周年假。所有封闭词表都从 `templates/` 读取，所以新增状态是改契约、检查器跟着走；否则把 `passed` 写成 `feasible` 会把所有依赖它的规则一起悄悄关掉，而且什么都不报。

`check_plan_consistency.py` 还检查页面**读起来**怎么样。交付计划里的文字本来就具体、有理由——没有「活力四射的画卷」，每条理由都扣着真实营业时间——但它依然读着像机器写的，因为破绽在**整齐划一**而不在辞藻。实测：50% 的叙述字段都是「事实——所以怎样」这一个模子；`focus` 与 `route_logic` 在一份计划里 4/5 天、另一份 5/8 天逐字相同，于是页面在两个标题下印同一句话。两者现在都被拒绝，破折号是限制在 35% 的字段以内而不是禁用。刻意**不做**违禁词表：那种表把「熙熙攘攘」换成「热闹」就算过关，而文字空洞如故，还会误伤旅客自己的说法。

**`fetch_plan_imagery.py`** 为计划里**真实存在的那些地方**配上经过验证、许可自由的照片——验证不过就一张不配。「上网搜点好看的图」这个朴素做法有四条会让旅行者更糟的失败路径，每一条都被正面回答而不是绕过去。**再分发**：只用 Wikimedia 素材，并在每张图旁渲染作者与许可，因为那正是它能待在这个文件里的前提。**准确性**：坐标接近只能证明「在那附近」，永远证明不了「拍的是它」——对真实 API 实测，「中央市场」匹配到了条目《阿利坎特轰炸》（相距 400 米，而且它的主图确实是市场），另有两个锚点退回到通用城市条目、会把同一张照片印在三个不同标题下。所以条目标题还必须确实是在讲被问的那个东西，退回通用条目一律拒绝，同一文件不得重复使用。**离线**：外链图片恰好在你人在国外时变成破图，还会把你在读哪份行程告诉第三方，所以字节内嵌、页面保持单文件自包含。**体积**：按限定宽度请求缩略图，缩放在服务端完成，本技能因此保持「仅标准库」。一份真实五日计划上验证通过 5 张照片耗时 13 秒（3 并发；8 并发会返回 HTTP 429），任何一格达不到这个标准就留空。**字节写到哪里**：写在计划**旁边**的 `<计划名>-imagery.json` 里，计划本身只留一个 `imagery_sidecar` 键。下面每个字节数都按 `write_json_atomic` 真正写盘的方式量取——`json.dumps(…, ensure_ascii=False, indent=2)` 再加一个换行——因为用别的编码量出来的数字，读者没法拿 `ls` 对上；在这份计划上，这个编码逐字节复现了它在磁盘上的大小。曾经是内嵌写入：实测某份已交付计划 2,132,252 字节里，`imagery` 键序列化后占 2,047,820 字节 —— 96.0%，而同一工作区另外十四份计划只有 28,943 到 127,936 字节；而 SKILL.md 要求这一步在**验证阶段**跑，那时七个 agent 手里拿着同一个计划路径，闸门每报一条问题又把读者送回这个文件：一次读取是 2,132,252 字节，而同一份计划把载荷挪出去、换写上 sidecar 键之后只有 84,385 字节。`render_final_trip_html.py` 与 `save_trip_deliverables.py` 会依据计划自己的文件名或那个键自动找到 sidecar，**不需要新参数**（参数是会被忘记的东西）；计划指向的载荷不存在时它们**直接非零退出并报出路径**——没有任何闸门统计 `<img>`，静默少了照片的页面看起来和正确页面一模一样。写入走 `os.replace` 原子替换，因为就地覆盖会让并发读者读到半份计划：实测把一份 2,023,900 字节的计划重写 40 次、同时有一个并发读者，就地覆盖读出 212 次解析失败，走 `os.replace` 是 0 次。总量上限是 `MAX_IMAGERY_TOTAL_BYTES` = 4,000,000 字节——此前所有上限都是按单张图算的。

**`plan_visuals.py`** 用计划自身已有的数字画四张内嵌 SVG 图：当天各站点的真实相对位置、每日步行分钟、预算构成与上限占用、以及当天固定时间点在时钟上的分布。此前交付的页面是 96KB 纯文本、零张图，而其中最难看出来的，恰恰是旅行者最需要判断的东西——这一天是紧凑一团还是横跨全城、哪天最费腿、钱花到哪去了。画这些不需要联网、不需要许可、不需要下载，代价约 15KB。两条用代价换来的规则：图表**按比例缩放而不是截断**（早先那版横向 SVG 在手机上只显示当天前两个站点，而且看起来是完整的）；以及**宁可退化成没有，也不退化成谎言**——步行图的初稿拿每天的总步行量去比「单次连续步行上限」，把一份真实计划的五天全部标成超限，而实际没有任何一段接近上限。

**`trip_timer.py`** 记录一次规划的真实耗时，并把「机器在算」和「在等旅行者」分开统计。它存在的理由是：`references/research-budget.md` 对 **token** 极其严谨——四天行程 1.18M、每个研究 agent 约 37k，全是实测——却**没有任何一处测量过分钟**，所以这个技能里关于「快不快」的每一句话都是猜的。两者的优化方向并不一致：计算是 fan-out，它的墙钟时间取决于最慢那个 agent 而不是总和，砍掉一个 agent 省 token 但一秒钟都省不下来；而旅行者的等待是一次有人参与的往返，没有上限。在一次合理的运行里，光是那个 checkpoint 就占掉近一半的实际时长，而这一点在任何 token 数字里都看不见。它记录的是时间戳而非时长，因为 `now` 是调用方唯一能诚实断言的东西；`audit_workspace.py` 会把多次运行的这个分布汇总出来。


**`probe_sources.py`** 回答一个这个 skill 反复答错的问题：这台机器到底能读到什么。同一份交付计划里有两次把一整类证据判为不可得——餐厅营业时间是读了列表页而没读详情页，酒店房价是读了 Booking.com 而当时早已探测可达的另一个源从没被要过内容。两句话都以「环境做不到」的形式到了旅行者眼前，而两句都不是环境的事实。本脚本按类别各探一个源，并且**只报可达性**、还明说这一点：200 只代表主机应答了，不代表页面给得出你要的字段，因为多数旅行站点靠 JavaScript 渲染。它还区分「这个客户端被拒」和「源确实挂了」——这个区分是它第一次运行时把自己搞错之后才学会的。

**`audit_workspace.py`** 用今天的闸门重跑工作区里已存的每一份计划，只报告、不改动任何文件。这个技能的每一条规则都是针对「当时正在建的那份计划」写的，从来没有回头看过：在一个真实工作区的十一份存档计划里，只有最新那份通过，其余每份 25–126 条发现。那个让人安心的解释 —— 「规则变严了，老计划当然会挂」 —— 对其中大多数并不成立。把发现逐条归类后可以看到，多数不是新增字段，而正是旅行者当初报告过的缺陷：每份 52–80 条无法地理编码的地图端点、21–31 条毫无依据的营业时间、五段步行速度快到只能是跑步。新存的计划从此带 `gates_passed` 戳，让这种归类不再是考古工作。它刻意不做任何修复：重新规划、重新核验还是丢弃，是旅行者的决定。默认输出是每份计划一行结论；发现本身在 `--verbose` 之后（配 `--plan <file>` 只看某一份），`--json` 给出同样的结论，外加每份计划一条记录、发现按 rule id 计数。

## 为什么 `--assistant auto` 永不自启第二个规划器

这条规则要连着它的来历看才讲得通：

- 最早的版本：只要 `CLAUDECODE` 被设置就另起一个无人看管的 agent —— 那个表示「已经有助手在处理这个工作区」的环境变量，反被当成了「再起一个」的信号。结果是同一个文件夹里出现两份互相矛盾的方案，无人看管的那份出发城市是错的、预算上限是被推翻的旧值、完全没有过敏信息，还给一位严重乳制品过敏的旅行者安排了德式啤酒馆晚餐，并存成了 `verification_status: verified`。
- 第一次修复：靠**列举助手名字**来判断。于是所有没被列进去的 harness —— Gemini CLI、Cursor、Copilot CLI、opencode、SDK agent —— 全都直接掉进启动分支。
- 第二次修复：改成**正面确认**裸交互终端（stdin 与 stdout 都是 tty）。可是 opencode、Cursor、Cline 既不设那些环境变量，又会分配完整的 pty，照样通过这项检测；只要 PATH 上有 `codex`，`auto` 依旧会拉起那个竞争的规划器。
- 所以现在**不再检测了**。tty 只能证明「挂了一个终端设备」，永远证明不了「是人打开的」。想要子进程就显式要：`--assistant codex`、`--assistant claude`，或 `TRAVEL_BUDDY_ASSISTANT=codex`。



## 手改方案时闸门报错怎么办

**校验器因为英文文本判我的页面不合格。** 非英文页面上，所有渲染器自带的字符串都必须翻译，**以可见文本形式打印出来的机器枚举值也算**。用封闭枚举，别自造类别名。

**一致性闸门拒绝了一个看起来没问题的方案。** 读它点名的内容 —— 那是算术，不是口味。`walking_burden` 必须以**数字**引用由当天各 segment 算出的步行总量，这样文案就无法和数据脱节。每张餐卡都需要一个 `route_anchor` 指向当天的某个停靠点（或者用 `off_route_justification` 说明这段绕路的代价），并且要么有 `venue_hours`、要么写 `hours_status: "unverified"`。路线总计必须等于其各段之和。已声明的 `cap_per_person` 不能在没有 `overrun_acknowledged` 的情况下被突破。

**地图按钮过不了校验。** 它必须是真正的导航 URL。中国大陆意味着 `https://uri.amap.com/navigation` 且 `from`、`to`、`mode` 都非空；`ditu.amap.com/place/...` 是 POI 页面，会被拒。另外记住高德用的是 GCJ-02 坐标系，WGS-84 坐标必须先转换，否则每条路线都会偏几百米。
